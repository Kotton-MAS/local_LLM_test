# 要件: ローカルLLM実行基盤（RTX 4070 Ti SUPER / 16GB）

> このドキュメントは Claude Code に実装を依頼するための要件定義です。実装はまだ行われていません。
> `(仮)` が付いた項目は推測で埋めたもので、着手前に確認が必要です。
>
> **v2 での更新**: RAG の対象データを Obsidian ノートに確定。埋め込みをローカル完結に確定。
> それに伴い Phase 3 を詳細化し、VRAM 予算を再計算しました。

---

## 目的

手元の GPU マシン上で、外部 API に依存しない LLM 実行環境を構築する。狙いは以下の3点。

1. **機密性** — 手元の文書を外部サービスに送らずに要約・検索・質疑応答を行う
2. **コスト非依存** — 大量の定型処理をトークン課金を気にせず回せる状態を作る
3. **学習** — 量子化・コンテキスト長・VRAM の関係を、自分の環境で実測しながら理解する

「クラウド API の完全な置き換え」は目的ではない。難度の高い推論やコーディングエージェント用途は API 側に残す前提で、**用途ごとに切り分けたハイブリッド構成**を最終形とする。

## スコープ

### やること

| # | 用途 | 内容 |
|---|---|---|
| A | 文書処理・要約・RAG | **Obsidian vault** を対象とした取り込み → 検索 → 回答生成のパイプライン |
| B | 日本語の文章作成・壁打ち | チャットUI 経由の対話。日本語品質でのモデル選定を含む |
| C | 学習・実験 | 複数モデル・量子化・コンテキスト長の比較を再現可能な形で回すハーネス |

### やらないこと（スコープ外）

- **コーディングエージェント用途** — 16GB VRAM では現状の最良選択肢（Qwen3-Coder-Next 30B Flash = 18GB 必要）が収まらないため対象外。既存の API ベースのツールを継続利用する
- **論文・PDF の取り込み** — 将来の拡張対象。**ただしローダ層は差し替え可能な設計とし、後から追加できる状態にしておく**（→ 設計上の必須要件）
- **モデルのファインチューニング / 学習** — 推論のみを扱う
- **マルチGPU / 分散推論** — 単一 GPU 前提
- **Obsidian プラグインとしての実装** — vault はファイルシステム経由で読み取る。Obsidian 本体への機能追加は行わない
- **vault への書き込み** — 読み取り専用。ノートの生成・更新は行わない
- **本番運用グレードの可用性設計** — 個人利用。冗長化・監視・認証は対象外

## ハードウェア制約と VRAM 予算

設計上の最大の制約であり、すべての判断の起点となる。

| 項目 | 値 |
|---|---|
| GPU | NVIDIA GeForce RTX 4070 Ti SUPER |
| VRAM | 16GB GDDR6X |
| メモリ帯域 | 672 GB/s |
| OS | Linux（Ubuntu 系） |

### 「収まる / あふれる」の境界

VRAM 使用量は **重み + KV キャッシュ + オーバーヘッド** で決まる。重みだけを見て判断してはならない。

| パラメータ規模 | Q4 相当での重み | 16GB での判定 |
|---|---|---|
| 7〜8B | 約 4〜5GB | 余裕あり |
| 12〜14B | 約 8〜9GB | 快適。KV キャッシュにも十分な余地 |
| 20B（MXFP4） | 実測 11.32GiB | 収まるが **128k は VRAM 内に収まらない**。実測で num_ctx=65,536（合計 13.68GiB）までが 100% GPU、98,304 で CPU オフロード（訂正 2026-08-22 / `docs/phase0-vram-measurements.md`）|
| 22B | 約 15GiB | 分水嶺。コンテキストを伸ばすと破綻する |
| 27〜32B Dense | 16GB 超過 | **CPU オフロード必須。速度が実用域を下回る** |

### RAG 構成での同居問題 ← v2 で追加

埋め込みをローカル完結にしたことで、**生成モデル・埋め込みモデル・リランカーが同じ 16GB を奪い合う**。これは今回の設計における最大の技術的論点である。

| 構成 | 生成 | 埋め込み | リランカー | 合計目安 | 判定 |
|---|---|---|---|---|---|
| **構成1（RAG 既定）** | Qwen3-14B Q4_K（実測 7.81GiB） | ruri-v3-310m | BGE Reranker v2-m3 | **実測 12.53GiB 累計 / 増分 11.97GiB** @16k（2026-08-23。較正後見積り 11.98GiB と 0.01GiB 一致） | **同居可能（予算 14.0GiB 内）** |
| **構成2（長文要約時）** | gpt-oss-20B MXFP4（実測 11.32GiB） | — | — | **実測 13.68GiB @64k**（100% GPU） | 埋め込み・リランカーを退避すれば可。128k は不可 |
| 構成3（非推奨） | gpt-oss-20B | ruri-v3-310m | BGE Reranker v2-m3 | 較正後見積り 16.09GiB @128k | 予算超過。起動時に停止する |

**設計方針:** 単一の常駐構成に固定せず、**プロファイルとして切り替え可能にする**。

- RAG の対話は構成1を既定とする（同居できて、リランカーまで載る）
- 長文を読ませる要約タスクのときだけ構成2に切り替える（実測で VRAM 内に収まる上限は 64k。128k は CPU オフロードになる）
- リランカーは実測 0.28GiB / 50ペア 140ms（2026-08-23、別ランタイム llama-server）と軽量なため、構成1では常時有効にできる

## アーキテクチャ

```
┌─────────────────────────────────────────────┐
│ L4: インターフェース                          │
│   - チャットUI（Open WebUI）  ← 用途 B         │
│   - CLI                      ← 用途 A / C     │
├─────────────────────────────────────────────┤
│ L3: アプリケーション                          │
│   - RAG パイプライン          ← 用途 A         │
│   - モデル比較ハーネス        ← 用途 C         │
├─────────────────────────────────────────────┤
│ L2: 推論クライアント（Python ライブラリ）       │
│   - OpenAI 互換 API のラッパ                   │
│   - モデル切替 / VRAM プロファイル管理           │
├─────────────────────────────────────────────┤
│ L1: ランタイム                                │
│   - Ollama（OpenAI 互換エンドポイントを提供）    │
└─────────────────────────────────────────────┘
```

**Ollama を第一候補**とする。モデル取得が 1 コマンドで済み、OpenAI 互換 API が標準で提供され、Linux でのセットアップが単純なため。

OpenAI 互換 API を全層の共通境界とすることで、ランタイムの差し替え（vLLM 等）、ローカルと外部 API の切り替え、Open WebUI などの既存クライアント接続が、いずれも設定変更のみで可能になる。**注記（2026-08-22 / D-10）: 層の共通境界は `ChatClient` Protocol（L2 内部の抽象）であり、ワイヤプロトコルではない。** ローカル Ollama では OpenAI 互換経路が `options.num_ctx` を無視するため、ネイティブ `/api/chat` を使う（送出経路は `runtime.kind` で設定から選ぶ）。

## RAG パイプラインの詳細設計（用途 A）

```
Obsidian vault
  ↓ ① ローダ（差し替え可能な抽象）
  ↓ ② パース（frontmatter / wikilinks / 見出し構造）
  ↓ ③ チャンク分割（見出しベース）
  ↓ ④ 埋め込み（ruri-v3-310m）
  ↓ ⑤ ベクトルストア（Chroma）
  ↓ ⑥ 検索 → ⑦ リランキング → ⑧ 回答生成
```

### ① ローダ

- vault のルートパスを設定で指定。**読み取り専用**
- `.obsidian/` 配下、添付ファイル（画像・PDF 等）、`.trash/` を除外
- 除外パターンは設定ファイルで追加可能にする
- **将来 PDF ローダを追加する際、このインターフェースの実装を1つ足すだけで済むこと**（他層の変更を要しない）

### ② パース

Obsidian 固有の記法の扱いを明示する。

| 要素 | 扱い |
|---|---|
| YAML frontmatter | **メタデータとして抽出**。本文テキストには混ぜない（埋め込みのノイズになる） |
| `[[Note Name]]` | **リンク先の表示テキストに解決**して本文に残す |
| `[[note\|alias]]` | **alias（表示テキスト）に解決**。例: `[[weekly-review\|weekly review]]` → `weekly review` |
| タグ `#tag` | メタデータとして抽出。フィルタ条件に使えるようにする |
| 見出し階層 | チャンクのコンテキストとして保持（③で使用） |

wikilinks を生の `[[...]]` のまま埋め込みに渡すと、埋め込みモデルにとってノイズになる。リンクの構造情報が必要な場合は、本文から分離してメタデータ側に保持する。

### ③ チャンク分割

**見出しベース分割を採用する。** 全文を1チャンクとする方式は短いノートには有効だが、複数見出しを持つ長いノートでは信号が分散して検索精度が落ちる。

- 分割単位は見出し。**上限 240 トークン目安**（設定可能とする）
- **見出しの階層構造をチャンクのコンテキストとして保持する**（例: `プロジェクトA > 設計 > データモデル`）。これによりセクション単位のクエリマッチが向上する
- 参考事例では、全文チャンク方式の検索精度 67.9% に対し、見出しベース分割で 75% まで改善している

### ④〜⑤ 埋め込みとベクトルストア

- 埋め込みモデルは `ruri-v3-310m`。設定で差し替え可能にする
- ベクトルストアは **Chroma**（ローカル保存、コサイン類似度）を初期採用。データ量が増えた場合に備え、ストア層も抽象を挟んで差し替え可能にする
- **差分更新必須**: 再実行時は mtime とコンテンツハッシュで変更を検出し、変更されたノートのみ再インデックスする。vault は日常的に更新されるため、毎回フルリビルドは実用にならない

### ⑥〜⑧ 検索・リランキング・生成

- 検索で Top-K を広めに取得し、リランカーで絞り込む
- 回答には **参照したノートのパスと見出し位置を必ず含める**。出典を提示できない回答は不可
- インデックスに根拠がない場合、捏造せず「情報がない」旨を返す

### 既知の失敗パターン（評価セットに含めること）

参考事例で報告されている典型的な失敗。これらを評価質問に意図的に含め、改善の有無を測れるようにする。

1. **セマンティックな隣接誤り** — 関連ノートは引けるが、目的のノートではない（最も件数が多い）
2. **ダッシュボード型ノート** — 表構造で意味を表現するノートは埋め込みに乗りにくい
3. **語彙不一致** — 比喩表現や独自の言い回しで検索が外れる
4. **スパースなノート** — リンクリストのみのノートは分割後にマッチしにくい

将来の改善余地として、vault のグラフ構造（バックリンク、被参照数）をリランキング信号に使う案がある。初期実装には含めない。

- **入力（取り込み時）**: Obsidian vault のルートパス

- **入力**: 単一の TOML スイートファイル（`suites/*.toml` に `[suite]` / `[[models]]`（比較対象モデルのリスト） / `[[prompts]]`（評価用プロンプト集）を収める）
- **出力**: `results/<suite_id>/<実行時刻>-<run_fingerprint 先頭12桁>/` に `report.md`（モデル比較の Markdown 表 + 応答）・`records.jsonl`（1 実行 1 行の生ログ）・`run.json`（再現条件と集計）。各実行につき生成速度・プロンプト処理速度・使用 VRAM・設定コンテキスト長を記録

## 制約

### 技術的制約

- 言語は Python。新規プロジェクトとして構築する
- 依存管理・Lint・型チェック・テストの構成は既存の `RC_basic_lab` に合わせる (仮)（uv / ruff / mypy / pytest）
- 推論ランタイムへの直接依存をアプリケーション層に持ち込まない。L2 の抽象を必ず経由する
- モデル名・コンテキスト長・エンドポイント・vault パスはハードコードせず設定ファイルで管理する
- **vault への書き込みを行わない**ことをコード上で保証する（読み取り専用でオープンする）

### 非機能要件

- **VRAM プロファイル**: 生成・埋め込み・リランカーの組み合わせをプロファイルとして定義し、起動時に想定 VRAM 使用量を算出してログ出力する。16GB を超える組み合わせは起動時に警告して停止する
- **エラー処理**: ランタイム未起動・モデル未取得・OOM・vault パス不正の4つは、原因が特定できるメッセージを出す。スタックトレースのみで終わらせない
- **ログ**: 比較ハーネスと RAG 評価の結果は再現可能な形で永続化する。実行日時・モデル・量子化・全パラメータを含める
- **性能**: 対話用途で生成 30 t/s 以上を下回る構成は選定しない。RAG のクエリ応答は検索＋リランキング＋生成開始まで 2 秒以内 (仮)

## 段階的な実装計画

### Phase 0: 環境構築と実測

CUDA ドライバ確認 → Ollama 導入 → モデル取得 → 単発推論の疎通確認。
`nvidia-smi` で実測 VRAM を記録し、上記の予算表が自環境で成立するか検証する。

### Phase 1: 推論クライアント層（L2）

OpenAI 互換 API のラッパ。モデル切替、VRAM プロファイル管理、コンテキスト長の設定と見積り。以降すべての土台。

### Phase 2: モデル比較ハーネス（用途 C）

同一プロンプト集を複数モデルに投げ、応答と速度指標を並べて出力する。
**用途 B のモデル選定と、埋め込み構成の最終判断（ruri-v3 単体 vs ハイブリッド）は、このハーネスの結果に基づいて行う。**

### Phase 3: RAG パイプライン（用途 A）

上記「RAG パイプラインの詳細設計」を実装する。着手前に **評価質問セットを先に作る**（参考事例では手作りの28問で検証している）。評価セットなしに実装すると、改善したかどうかが判断できない。

### Phase 3.5: 拡張（任意）

PDF ローダの追加。グラフ構造をリランキング信号に使う実験。

### Phase 4: チャットUI 接続（用途 B）

Open WebUI を導入し L1 のエンドポイントに接続。Phase 2 で選定したモデルを既定にする。
